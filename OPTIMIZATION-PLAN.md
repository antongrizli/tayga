# План снижения CPU TAYGA CLAT и сбора perf-сессий

Дата: 2026-09-16. База: `8a028c787c86389a75dd4ef8cc01c9501133e966`.
Проверены `nat64.c`, `addrmap.c`, `tun.c`, `conffile.c`, `tayga.c`, Makefile,
`benchmark-clat.sh`, `Dockerfile.benchmark` и соседний `clat-start.sh`.
Это план последующих работ; новые perf-сессии в рамках этого аудита не записывались.

## 1. Цель и критерий успеха

Цель — снизить CPU при одинаковой полезной скорости 200 и 300 Мбит/с,
а не только увеличить предельную скорость. 500 Мбит/с — запас для стенда.
Здесь Мбит/с = 10^6 бит/с; 200 МиБ/с — примерно 1678 Мбит/с, другая нагрузка.

Предлагаемый критерий заметного улучшения: минимум 20% относительного снижения
CPU TAYGA при 300 Мбит/с, без ухудшения потерь и задержек. Отдельно измерять
CPU всего роутера: снижение с 50% до 40% — 20% относительно исходного значения,
но 10 процентных пунктов. Это цель, а не обещание результата.

Если TAYGA занимает только долю f общей работы CPU, то сокращение его затрат
на долю r уменьшит общие затраты приблизительно на f*r при той же нагрузке.
Например, f=0.3 и r=0.3 дают лишь 9% общего снижения. Сначала измерить f.

## 2. Что показывает код

| Участок | Наблюдение | Следствие |
|---|---|---|
| `conffile.c:config_init/config_validate` | Кэш по умолчанию 8192 записей; отключается только если первые записи обеих таблиц — RFC6052. В CLAT есть явный статический map перед RFC6052 | Для текущего CLAT кэш остаётся включённым; проверить это диагностикой при запуске |
| `addrmap.c:map_ip4_to_ip6/map_ip6_to_ip4` | Даже cache hit берёт общий `cache_mutex` и пишет `last_use`; на cache miss добавляются `map_mutex` и вставка в кэш | Предыдущий опыт без `map_mutex` не исключает конкуренцию за `cache_mutex` |
| `tun.c:tun_read`, `nat64.c:xlate_*` | Один `read` на входной пакет, один `writev` на выходной; фрагментация увеличивает число записей | Системные вызовы и сетевой стек могут стоить больше самой трансляции |
| `tun.c:tun_setup`, `tayga.c:worker` | При workers>0 основная очередь отсоединяется, создаются ровно workers рабочих очередей | workers=3 — три обработчика пакетов плюс служебный главный поток, а не четыре обработчика |
| Локальный diff `nat64.c/tun.c/tayga.h` | FD входной очереди передаётся в запись переведённого пакета и локального ICMP | Перспективный эксперимент с очередями; нужна независимая проверка выигрыша |
| `nat64.c:xlate_payload_*` | Для обычного TCP/UDP checksum корректируется инкрементально | Полный SIMD-пересчёт payload не является первым кандидатом; особый случай — UDP с нулевой checksum |
| `nat64.c:log_pkt4/log_pkt6` | Форматирование адресов выполняется после проверки флагов логирования | Не объявлять логирование главным источником затрат без профиля |
| `Makefile:help` | Упоминает WITH_URING/WITH_SEG_OFFLOAD, но проверенный путь сборки не реализует эти режимы | Передача таких переменных make сама по себе ускорение не включает |

## 3. P0 — сделать результаты воспроизводимыми

Предыдущие 4.76 → 5.07 Гбит/с (~6.5%) и 0.600 → 0.557 core/Gbps (~7.2%)
считать предварительными наблюдениями. Это короткие локальные upload-прогоны,
не доказательство снижения CPU на Chateau. Есть неполные прогоны без результата
download; их нельзя считать успешными.

Перед следующими оптимизациями исправить стенд:

1. Сохранять iperf JSON, stderr, exit code и логи процессов даже при ошибке.
   Не оставлять единственную копию JSON в shell-переменной под `set -e`.
   Проверять поле `error`, ожидаемое число направлений и длительность.
2. Выбирать PID точно. `ip netns exec clatns pgrep tayga` меняет сетевой namespace,
   но НЕ PID namespace: команда может найти PLAT и другие экземпляры TAYGA.
   При прямом запуске `ip netns exec ... clat-start.sh &` сохранить `$!`, дождаться
   `exec tayga` и проверить `/proc/PID/exe`, cmdline и netns. Для Docker использовать
   PID, видимый Linux-хосту, и проверить, что это TAYGA, а не tini/entrypoint.
3. Готовность проверять по маршрутам, процессу и пробному TCP/ICMP, а не только pgrep.
4. Параметризовать workers, rate, протокол, размер пакета, направление и MTU.
   Сейчас workers=3 задан жёстко, скорость не ограничивается.
5. Синхронизировать окна CPU и трафика. Сейчас CPU считается вместе с iperf `-O`,
   а итоговая скорость — без пропущенного интервала. Для простого варианта выполнить
   отдельный прогрев, затем измерять тест без `-O`; для точного — общие временные границы.
6. 20 потоков одного клиента не называть 20 клиентами. Добавить 20 адресов/клиентов,
   соединения к нескольким назначениям, короткие соединения и оборот записей кэша.
7. Сохранить два стенда: микротест CLAT и полный LAN → NAT44 → CLAT → NAT66 → PLAT
   → IPv4-server. Текущий benchmark заканчивается на IPv6 iperf-сервере, не содержит
   NAT66 и PLAT и не воспроизводит весь путь Telekom.
8. Записывать cpu time процесса (user+system), RSS/PSS, переключения контекста,
   migrations, pps, retransmits/потери, p50/p95/p99 RTT, CPU ядра и всего хоста.
   Сумма CPU отдельных потоков не должна повторно включать агрегат процесса.
9. Проверять происхождение бинарника. В существующей тестовой сборке печатался
   старый `1fcb318`, хотя HEAD=8a028c7: скопированный `version.h` может не обновиться,
   если make не видит корень git. Сохранить git diff, хэш бинарника и образа;
   генерировать корректный version.h при сборке и принудительно пересобирать.
10. Закрепить digest базового образа, compiler/libc/iperf версии; `alpine:edge`
    без digest недостаточно. Изменение только заголовка тоже должно пересобирать
    TAYGA: сейчас зависимости target не перечисляют `tayga.h`.

Матрица: workers=0/1/2/3; 1 и 20 клиентов; TCP upload/download/bidirectional;
200/300/500 Мбит/с и unlimited отдельно; UDP payload 64/256/1200 байт с заданным pps.
workers=0 обрабатывает пакеты в главном потоке, не выключает TAYGA.
При iperf `-P 20 -b 15M` скорость задаётся на поток: суммарно примерно 300 Мбит/с.
UDP 1200 байт при 300 Мбит/с — примерно 31250 datagrams/s без учёта заголовков.
При этом контролировать фактически принятые байты, а не только заданный rate.

Начать с 300 Мбит/с, 20 потоков, обоих направлений, workers=1/3. Для кандидата,
показавшего выигрыш, расширить матрицу. Прогрев 15 секунд, измерение 60 секунд,
не менее 5 чередующихся A/B повторов. Сохранить медиану и разброс, не лучший прогон.
Не запускать конкурирующие варианты одновременно. Использовать одинаковые CPU,
частоты, offload, qdisc и доступную память. Локальная VM на Apple Silicon полезна
для поиска функций, но не моделирует стоимость инструкций CPU Chateau.

## 4. Очерёдность оптимизации

### P1 — число workers и закрепление существующего исправления очередей

- Сравнить upstream и текущий diff при одинаковых rate/pps; отдельно проверить
  нагрузку одного worker и равномерность распределения потоков по очередям.
- При 200–300 Мбит/с один или два worker могут тратить меньше суммарного CPU,
  чем три: меньше конкуренции и пробуждений. Выбрать минимум CPU при сохранении
  запаса пропускной способности и приемлемого p99; не фиксировать один поток вслепую.
- Не вводить busy polling: он может увеличить максимальную скорость ценой CPU в простое.
- Проверить все семь путей `writev`, локальный ICMP, ошибки ICMP с вложенными пакетами,
  фрагментацию и workers=0. Наличие multiqueue ещё не доказывает выигрыш от смены FD.

### P2 — специализированный путь для неизменяемой CLAT-карты

Это первый кандидат на существенное уменьшение пользовательских CPU-затрат,
если perf покажет `cache_mutex`, hash lookup, cache maintenance или futex.

1. При старте распознавать допустимую конфигурацию: один CLAT map /32↔/128,
   адреса самого транслятора, один PREF64; нет dynamic-pool и reloadable map-file.
2. Построить неизменяемые правила прямого преобразования: точное сравнение CLAT-адреса,
   затем вставка/извлечение IPv4 в PREF64. Обходить ОБА общих кэша и map mutex
   только для доказанно неизменяемой конфигурации.
3. Сначала отдельным экспериментом отключить cache для этого режима и сравнить:
   короткий список карт может быть дешевле hash+mutex. Затем убрать map mutex.
   Это отличает гипотезу от прежнего неубедительного опыта.
4. Сохранить приоритет статических карт, локальные адреса, hairpin-проверки,
   запрет private IPv4 с well-known prefix, все поддерживаемые длины RFC6052.
   Быстрый путь /96 может иметь общий fallback для остальных префиксов.
5. Не переносить запрет блокировок на dynamic NAT64/reload. Для общей конфигурации
   рассматривать per-worker cache только с продуманной инвалидацией; это дороже по RAM.

Ожидаемое направление: меньше синхронизации и записей в общую cache line.
Процент выигрыша заранее неизвестен. Нужны профили cache-hit и cache-miss нагрузок.

### P3 — уменьшить packets/s при той же полезной скорости

- Проверить end-to-end PMTU, TCP MSS, DF и ICMP Packet Too Big. `offlink-mtu=1280`
  используется при фрагментации; это не равнозначно установке MTU TUN в 1280.
- Увеличивать MTU только после проверки пути оператора. Исключить повторную
  фрагментацию/ретрансляции; не отключать ICMP ради экономии CPU.
- Если профиль доминируется TUN/copy/segmentation: исследовать IFF_VNET_HDR,
  checksum/GSO offload и перевод метаданных IPv4↔IPv6. Это отдельная сложная работа,
  требующая поддержки ядром RouterOS и корректной обработки сегментов.
- `writev` объединяет части ОДНОГО пакета; это не пакетный batch.
  Нельзя заменить несколько TUN-записей одной writev и считать пакеты сохранёнными.
  `sendmmsg/recvmmsg` не являются прямой заменой read/write для TUN FD.
- io_uring рассматривать только после проверки доступности и профиля syscall overhead;
  не рассчитывать на него как обязательную зависимость RouterOS-контейнера.

### P4 — локальные изменения и компилятор по результатам perf

- Если горячая функция — checksum/parser, изучить `perf annotate`, ветвления,
  выравнивание и сгенерированные ARM64-инструкции. Не удалять проверки пакетов.
- Сравнить O2/O3/LTO, затем PGO на репрезентативных TCP/UDP/ICMP нагрузках.
  Проверить на отдельной нагрузке, не использованной для обучения PGO.
- `-mcpu=native` на Mac/Linux VM не годится для переносимого образа Chateau.
  Сначала подтвердить модель CPU и ISA роутера, затем экспериментировать с tune.
- При hot locks/cachelines исследовать per-worker counters и размещение данных;
  padding делать только после доказательства false sharing, с учётом RAM.

### P5 — если основная стоимость вне TAYGA

Если CPU расходуется на forwarding/conntrack/NAT66/LTE/Wi-Fi, переписывание checksum
не даст требуемого эффекта. Сравнить проводного клиента с Wi-Fi, native IPv6 с CLAT,
и долю IPv4-трафика. Исправная native IPv6-связность позволяет IPv6-сервисам обходить
CLAT. Это требует отдельной проверки маршрутизации LAN; отсутствие DHCPv6-PD не
исправляется оптимизацией TAYGA. FastTrack по выводу пользователя уже активен.
Kernel SIIT/Jool/eBPF нельзя считать просто устанавливаемой заменой в RouterOS:
сначала доказать доступность необходимых функций и прав на целевом ядре.

## 5. Где собирать perf

Основной стенд — управляемая Linux ARM64 VM либо ARM64 Linux-машина. macOS не запускает
Linux perf напрямую. Docker Desktop работает внутри Linux VM; её PMU, kernel symbols
и права могут быть ограничены. CHR не заменяет управляемую Linux VM для perf.
Установка perf в RouterOS-контейнер не гарантирует доступ к PMU/tracepoints ядра.
Не менять глобальные ограничения безопасности ради теста на рабочем роутере.

В Linux установить perf для текущего ядра, gcc/make, iproute2, iperf3, nftables,
sysstat, binutils и зависимости integration-тестов из `test/index.md`.
Профилировать с Linux-хоста или внутри одного PID namespace с TAYGA; `sudo` ниже
относится к выделенному Linux-стенду, а не к RouterOS/macOS.

### 5.1. Подготовка бинарника и паспорта сессии

Внутри git-копии исходника на Linux:

```sh
make -B CC=gcc CFLAGS='-O3 -flto -fno-plt -g -fno-omit-frame-pointer' LDFLAGS='-flto -Wl,--build-id'
SESSION="$(pwd)/perf-sessions/$(date -u +%Y%m%dT%H%M%SZ)-baseline-w3-300m-upload"
mkdir -p "$SESSION"
git rev-parse HEAD > "$SESSION/commit.txt"
git diff --binary > "$SESSION/source.patch"
cp tayga "$SESSION/tayga.debug"
sha256sum tayga > "$SESSION/binary.sha256"
uname -a > "$SESSION/kernel.txt"
lscpu > "$SESSION/cpu.txt"
gcc --version > "$SESSION/compiler.txt"
perf version > "$SESSION/perf-version.txt"
iperf3 --version > "$SESSION/iperf-version.txt" 2>&1
perf list > "$SESSION/perf-events.txt"
```

Запускать именно этот бинарник; не strip до завершения анализа. Обе сравниваемые
версии собирать одинаково. Отдельно подтвердить выигрыш production-сборкой без
профилирования, поскольку frame pointers и запись профиля меняют расходы.
Дополнить паспорт конфигурацией TAYGA, namespace-схемой, MTU/offload, скоростью,
размером пакетов, версиями libc/ядра, доступными CPU и частотами.

### 5.2. Точный PID и проверка возможностей

Стенд должен сохранять PID после exec TAYGA и держать процесс живым на протяжении
всех сессий. Следующие команды выполнять после старта исправленного стенда:

```sh
read -r TAYGA_PID < /run/tayga-bench.pid
test "$(cat /proc/"$TAYGA_PID"/comm)" = tayga
readlink /proc/"$TAYGA_PID"/exe
readlink /proc/"$TAYGA_PID"/ns/net
ps -L -p "$TAYGA_PID" -o pid,tid,psr,pcpu,comm
sudo perf stat -e task-clock -p "$TAYGA_PID" -- sleep 1
sudo perf stat -e cycles,instructions -p "$TAYGA_PID" -- sleep 1
```

Файл `/run/tayga-bench.pid` — требуемое дополнение стенда, сейчас автоматически
не создаётся. Не подставлять PID PLAT. При недоступном hardware PMU использовать
software events; не представлять их как измеренные cycles/IPC. При запрете также
software events перенести сбор на контролируемый Linux-хост.

### 5.3. Сессия A: CPU и счётчики без стека

Запустить устойчивую нагрузку на 90+ секунд в другом терминале. После прогрева
собрать 60 секунд и сопоставить с теми же интервалами iperf JSON:

```sh
sudo perf stat -x ';' -o "$SESSION/stat-software.csv" \
  -e task-clock,context-switches,cpu-migrations,page-faults \
  -p "$TAYGA_PID" -- sleep 60
```

При доступном PMU отдельным повтором той же нагрузки:

```sh
sudo perf stat -x ';' -o "$SESSION/stat-hardware.csv" \
  -e cycles,instructions,branches,branch-misses,cache-references,cache-misses \
  -p "$TAYGA_PID" -- sleep 60
```

Если часть событий не поддерживается, убрать именно их; сохранить сообщение об
ошибке. При сильном multiplexing разделить события на несколько одинаковых прогонов.
Среднее число занятых ядер = task-clock_ms / (elapsed_s * 1000).
core/Gbps = число ядер / принятые Gbit/s в том же временном окне.

### 5.4. Сессия B: стеки процесса

Отдельный повтор той же нагрузки, начальная частота 99 Hz:

```sh
sudo perf record -o "$SESSION/process.data" -e cpu-clock -F 99 \
  --call-graph dwarf,8192 -p "$TAYGA_PID" -- sleep 60
sudo perf report -i "$SESSION/process.data" --stdio --no-children \
  > "$SESSION/process-self.txt"
sudo perf report -i "$SESSION/process.data" --stdio \
  > "$SESSION/process-callgraph.txt"
sudo perf script -i "$SESSION/process.data" > "$SESSION/process.stacks"
sudo perf buildid-list -i "$SESSION/process.data" > "$SESSION/buildids.txt"
```

Сохранить stderr perf (lost samples и ошибки unwind). При недоступном DWARF использовать
`--call-graph fp` с этой же сборкой и проверить качество стеков. Если мало samples —
увеличить длительность; сначала проверить overhead, затем частоту.
Для горячей функции: `sudo perf annotate -i "$SESSION/process.data" --stdio -s map_ip4_to_ip6`.
При LTO функция может быть inline: смотреть родителя и строки исходника.

### 5.5. Сессия C: сетевой стек всего Linux-стенда

Процессный профиль не включает всю работу ksoftirqd/IRQ и соседних namespace.
На выделенной машине отдельно записать общий профиль:

```sh
sudo perf record -a -e cpu-clock -F 99 --call-graph fp \
  -o "$SESSION/system.data" -- sleep 60
sudo perf report -i "$SESSION/system.data" --stdio \
  --sort comm,dso,symbol > "$SESSION/system.txt"
mpstat -P ALL 1 60 > "$SESSION/mpstat.txt"
pidstat -t -u -w -p "$TAYGA_PID" 1 60 > "$SESSION/threads.txt"
```

Последние команды — отдельные повторения нагрузки либо параллельные наблюдатели
одного заранее спланированного окна. Записывать время начала/окончания каждого.
Снять `/proc/softirqs`, `/proc/net/softnet_stat`, `ip -s link` в нужных namespace
до/после. Разделить TAYGA, PLAT и генератор по comm/PID; общий профиль всей лаборатории
не равен CPU одного контейнера. Для подробных kernel-стеков нужны символы и поддержка
unwind ядра. На виртуальной машине host-side расходы гипервизора в этот профиль не входят.

### 5.6. Сессия D: блокировки и syscall, только по необходимости

Если видны mutex/futex или частые переключения, отдельный короткий сбор:

```sh
sudo perf stat -p "$TAYGA_PID" \
  -e syscalls:sys_enter_read,syscalls:sys_enter_writev,syscalls:sys_enter_futex \
  -o "$SESSION/syscalls.txt" -- sleep 30
sudo perf sched record -a -o "$SESSION/sched.data" -- sleep 15
sudo perf sched timehist -i "$SESSION/sched.data" -p "$TAYGA_PID" \
  > "$SESSION/sched.txt"
```

Предварительно проверить tracepoints в `perf list`. Отсутствие futex не доказывает
отсутствие затрат mutex: быстрый путь работает в userspace. `perf lock` не является
универсальным измерителем pthread mutex. Если нужен точный wait/hold time, добавить
в отдельную диагностическую сборку редкие выборочные per-thread замеры lock latency;
не оставлять измерения времени на каждом пакете в production.

### 5.7. Сессия E: проверка на Chateau

Во время фиксированной нагрузки с проводного клиента сохранить:

```routeros
/tool profile cpu=all
/system resource cpu print
/system resource print
/container print detail where name="telekom-nat64"
/ip settings print
/interface lte monitor lte1 once
```

`profile` интерактивный, завершить Ctrl+C после окна. Сравнить idle, native IPv6,
CLAT 200 и 300 Мбит/с; сохранить число клиентов, направление, длительность,
счётчики трафика, память и состояние радиоканала. Не запускать генератор нагрузки
на самом роутере. Повторить с той же конфигурацией и примерно теми же радиоусловиями.
Не использовать Torch/sniffer одновременно с итоговым замером FastTrack.

## 6. Условия переноса оптимизации в основной образ

- Штатный `make test` проверяет прежде всего конфигурацию; он не заменяет пакетные
  integration-тесты. Запустить `make integration` с зависимостями `test/index.md`.
- Проверить TCP/UDP/ICMP в обе стороны, UDP zero checksum, IPv4 options,
  IPv6 extension headers, фрагменты, PMTU/DF/PTB и ошибки с вложенными пакетами.
- Для изменений map/cache: overlapping maps, private/WKPF, hairpin, разные PREF64,
  dynamic NAT64, reload, workers=0/1/3, гонки; sanitizer-прогоны отдельно от performance.
- Полный 464XLAT: NAT44/NAT66, IPv4 только сервер, трафик LAN и самого роутера,
  отказ/восстановление PLAT. Затем длительный тест RAM и tail latency.
- Для каждого кандидата сохранить отдельный diff и A/B perf-сессии. Если экономия
  меньше разброса или увеличивает потери/p99, не объявлять улучшением.
- Сначала P0 → P1 → P2. Переходить к offload/PGO после профиля, показывающего,
  что их участок действительно ограничивает результат.

## 7. Состав архива perf-сессии и источники

Хранить: commit+diff, точный unstripped binary и build-id, конфигурацию, compiler/libc,
ядро/CPU/частоты, PID/TID, параметры трафика, JSON iperf, CPU/RAM/link counters,
perf.data, stderr perf, текстовые отчёты, timestamps, итоговую таблицу A/B.
Для анализа на другой машине сохранить matching библиотеки/debug symbols (при наличии
использовать `perf archive`) и исходники. DWARF-профиль может содержать фрагменты стека;
для публикации использовать лабораторный трафик и предварительно проверить архив.

- [perf stat](https://man7.org/linux/man-pages/man1/perf-stat.1.html)
- [perf record: events, call graphs, PID](https://man7.org/linux/man-pages/man1/perf-record.1.html)
